# v4.5.1 maintenance-lane Phase-0 model

## Decision

`v4.5.1` is **not publishable by the current A-H chain**. This change is an
inert protocol model only. It is not a collector, admission gate, signature
verifier, byte verifier, activated lane, or live proof that the modeled GitHub
state exists. It creates no branch, pull request, key, secret, variable, tag,
release, or GitHub setting.

The model is
[`security/v4.5.1-maintenance-lane.json`](../security/v4.5.1-maintenance-lane.json).
The local checker is
[`tools/ci/validate_v451_maintenance_control.py`](../tools/ci/validate_v451_maintenance_control.py).

## Why the current release chain is not reusable unchanged

1. Current A-H couples the trusted workflow revision to the release source.
   A maintenance patch needs reviewed workflow bytes from protected `main` and
   a different target descended from the retained post-`v4.5.0` state.
2. Current H creates a lightweight tag at a commit. It does not consume a
   separately prepared, maintainer-signed annotated tag object.
3. The tag ruleset grants bypass to the generic `DeployKey` actor class. That
   is safe only while an independently collected complete repository listing
   proves there is exactly one write-enabled deploy key and identifies it.
4. GitHub can list Environment secret metadata but cannot disclose the secret
   value. A future trusted H step must derive the public key from the private
   secret and bind it to the sole repository deploy key before any tag mutation.
5. A commit cannot contain its own future commit SHA. Therefore the checked-in
   model cannot activate by replacing its `POST_MERGE_REQUIRED` values. The
   workflow commit/tree and one-shot authorization must remain external,
   owner-controlled pins in a future implementation.

## What Phase 0 freezes

- literal repository/owner IDs, refs, retained maintenance base commit/tree,
  candidate scope, version, and tag name;
- the complete branch-protection shape and exactly eleven check/App-ID pairs;
- the active `v*` tag ruleset and its DeployKey-only bypass class;
- four protected Environments, reviewer IDs, and `main`-only deployment
  policies;
- raw-Git modes and blob IDs for seven workflows and the frozen control,
  policy, verifier-pack, and validator inputs;
- the maintainer verification key's literal normalized repository path
  (`security/v4.5.1-maintainer-signing.pub`) and regular-file mode (`100644`);
  its post-merge blob ID and fingerprint remain external owner pins, and the
  observation shape must bind that exact path to that exact blob in the pinned
  trusted-workflow tree;
- exactly seven run roles: `A -> B -> CD -> E -> F -> G -> H`; C and D are jobs
  in one CD run, and all run IDs must be distinct;
- two non-ambiguous checkpoints: before publication requires exactly A through
  G; after H and before retirement requires exactly A through H;
- the names of the external owner variables, signing-key requirements, release
  asset names, publication Environment, publication secret, and temporary
  deploy-key title.

The independently reviewed live snapshot confirmed the eleven checks, tag
ruleset, four Environments, and retained base values at that point in time. It
does not prove they remain unchanged for a later run.

## Publication authority requirement

A future out-of-process, owner-authenticated, bounded, fully paginated GitHub
collector must enumerate the complete repository deploy-key list. The protocol
then requires exactly one item with `read_only=false`, and that item must equal
the owner-pinned ID, title, Ed25519 public key, creation time, `verified=true`,
`enabled=true`, and derived OpenSSH SHA-256 fingerprint. Additional read-only
keys do not gain tag-write authority.

The same collector must enumerate the exact
`evoguard-release-publication` Environment secret inventory. It must contain
only `EVOGUARD_RELEASE_TAG_DEPLOY_KEY` with the owner-pinned creation/update
metadata. A `sole_write_enabled: true` field or another candidate-provided
boolean is not accepted as a substitute for enumerating the items.

GitHub secret metadata cannot bind a private value. A future trusted-main H job
must derive the public key and fingerprint from the Environment secret and
compare both to the sole write-enabled deploy key before tag mutation. Phase 0
defines this receipt shape but does not execute or authenticate it.

## Explicit non-authority boundary

`validate_observation_shape(...)` validates only closed normalized data shapes.
It performs **no** GitHub authentication, raw-Git collection, signature
verification, retained F/G byte verification, tag-object parsing, Environment
approval binding, or temporal control-plane binding. Its formats say
`OBSERVATION_SHAPE` and the local-verifier input says
`NON_AUTHORITATIVE_PHASE0_SHAPE_ONLY`.

There is deliberately no `verified: true` signature proof. Future commit/tag
verification must operate on raw object bytes with a pinned key and produce
retained verifier receipt bytes under a separately trusted implementation.
Phase-0 tests can reject inconsistent receipt *shapes*; they cannot establish
that a signature was cryptographically checked.

Likewise, a release asset digest cannot prove admission by equating two fields
in one object. The model records blockers requiring independent retained F and
G byte receipts plus downloaded GitHub release-asset bytes. Until that exists,
the release section validates names/digest syntax/immutability shape only.

The raw tag section is also shape-only. It does not parse canonical Git tag
bytes or bind tagger, message, signature, and encoding. A future parser must
bind all of `object`, `type`, `tag`, `tagger`, `message`, `signature`, and
`encoding`, then push the verified tag-object SHA rather than the target commit.
The decoded raw tag object is capped at **32 KiB (32,768 bytes)**. This is a
conservative pre-Base64 bound for GitHub's 48 KiB configuration-variable limit:
32,768 bytes encode to 43,692 Base64 characters, leaving margin for transport
and representation overhead. The size bound is enforced both in the contract
and in the post-publication observation shape.

Repository paths used for the signing root are not free-form filesystem paths.
The validator accepts only a normalized relative POSIX path: no absolute path,
drive prefix, backslash, empty/`.`/`..` segment, duplicate separator, or trailing
separator. This prevents a future collector from resolving the externally
pinned key outside the trusted Git tree or through an alias.

## Time and retirement requirements

A point-in-time settings snapshot is insufficient. A future implementation must
bind a fresh owner-control-plane observation to each exact run ID/attempt and
to each protected Environment approval before secret access.

All collected timestamps use canonical whole-second UTC RFC3339 syntax
(`YYYY-MM-DDTHH:MM:SSZ`) and are calendar-parsed, so impossible dates, offsets,
fractional seconds, hour 24, and leap-second spellings fail closed rather than
passing a regular-expression shape check.

After H, a separate retirement checkpoint must:

1. disable the one-shot authorization;
2. delete the raw-tag-object variable;
3. delete the temporary repository deploy key;
4. delete `EVOGUARD_RELEASE_TAG_DEPLOY_KEY` from the publication Environment;
5. retain the immutable release and signed annotated tag;
6. emit a separately signed, owner-collected retirement receipt bound to the
   release ledger.

Phase 0 records these as unimplemented blockers and does not claim retirement.
The `blockers` field is an exact closed set of stable IDs, not an arbitrary
non-empty explanation list. Removing a required ID, adding an unknown ID, or
duplicating one invalidates the model; prose explanations remain in this
document so changing wording cannot silently weaken the machine contract.

## Activation boundary

The checked-in contract accepts `enabled=false` only. Workflow SHA/tree,
one-shot value, maintainer-key blob/fingerprint, deploy-key identity, and secret
metadata remain invalid `POST_MERGE_REQUIRED` values. The signing-key repository
path and mode are already literal trusted inputs. The checker CLI implements
only `--check-inert`.

A separate future implementation must consume owner pins from outside the
commit, implement authenticated collectors and cryptographic/byte verifiers,
time-bind every checkpoint, redesign A-H, and implement retirement. Until every
blocker is independently closed, the only correct operational result is
fail-closed.
