# v4.5.1 maintenance-lane trust boundary

## Current decision

`v4.5.1` is **not publishable by the current A–H chain**. The source contract
for a safe one-time maintenance lane now exists, but it is deliberately inert.
No tag, release, maintenance branch, repository setting, Environment setting,
or signing authority is created by this change.

The literal machine-readable contract is
[`security/v4.5.1-maintenance-lane.json`](../security/v4.5.1-maintenance-lane.json).
Its validator is
[`tools/ci/validate_v451_maintenance_control.py`](../tools/ci/validate_v451_maintenance_control.py).

## Why the existing chain cannot be reused

This is a mechanical conflict, not a documentation concern:

1. The current A–H workflows repeatedly require `GITHUB_WORKFLOW_SHA`,
   `GITHUB_SHA`, the protected `main` head, and the release target SHA to be the
   same object. A maintenance run must instead execute reviewed workflow bytes
   from protected `main` while admitting a different source commit descended
   from the retained post-`v4.5.0` state.
2. Current H rejects a pre-existing tag and creates `refs/tags/v*` directly.
   That produces a lightweight tag. It cannot establish a maintainer-signed
   annotated tag, and a GitHub Actions verification badge is not a substitute
   for a pinned maintainer signing key.
3. The checked repository state has no `maintenance/v4.5` or
   `release/v4.5.1` branch. Therefore no exact branch protection or exact open
   PR can currently be observed.
4. The protected Environments were designed for the default-main lane. Their
   deployment-branch rules must be reviewed as GitHub control-plane state;
   changing YAML cannot prove or alter those settings.

Changing only A, or replacing `main` with a workflow input, would let a mutable
ref choose the source of policy, code, or publication. Copying current `main`
into a `4.5.1` patch would also mix the `4.6.0.dev0` line into the stable
maintenance release. Both are rejected.

## Closed contract

The validator accepts only one repository and these literal identities:

| Role | Literal identity |
| --- | --- |
| Trusted workflow source | `EvoRiseKsa/EvoOM-Guard-m@refs/heads/main` |
| Frozen maintenance base | `maintenance/v4.5` at `2a8f012a8b6a5b62b9b0990207db8e0aed589795` |
| Candidate PR head | `release/v4.5.1` in the same repository |
| Version and tag | `4.5.1` and `v4.5.1` |

Before candidate execution, a future collector must obtain GitHub API state
and the trusted validator must require all of the following:

- repository ID and owner ID equal the reviewed literal values;
- `main` and `maintenance/v4.5` are protected, with exactly equivalent strict
  checks, stale-review dismissal, CODEOWNERS, last-push approval, administrator
  enforcement, conversation resolution, and force-push/deletion prohibitions;
- `maintenance/v4.5` remains at the retained post-`v4.5.0` commit and tree;
- exactly one open PR has literal base/head branches and a same-repository head;
- its head has exactly one parent—the frozen maintenance base—and no merge-parent
  ambiguity;
- `MANA-awam` approved the exact current head and every exact protected check
  completed successfully on that head;
- the source commit has a valid GitHub verification bound to a reviewed,
  pinned maintainer signing-key fingerprint;
- changed paths are inside the frozen CLI-fix, test, version, status, and
  release-document scope;
- every A–H handoff binds the same trusted workflow commit/blob set, the same
  different target source commit, and the exact upstream run ID and attempt;
- publication has one annotated `v4.5.1` tag signed by the pinned maintainer
  key, one immutable release, and exactly `evo-guard.pyz`,
  `evo-guard.spdx.json`, and `SHA256SUMS`.

The negative contract tests cover default-main/maintenance substitution,
unprotected or moved branches, alternate repositories, moved PR heads,
multiple parents, stale attempts, workflow-blob substitution, unsigned source
commits, unsigned or lightweight tags, and release-scope expansion.

## Required redesign before activation

1. Land this inert contract on protected `main` and record the exact trusted
   workflow commit and seven workflow blob IDs.
2. Create `maintenance/v4.5` at the exact frozen base and apply protection
   equivalent to `main`. This is a GitHub administration action, not a source
   change.
3. Pin a reviewed maintainer signing public key and fingerprint in the trusted
   source contract. Produce the one-parent `release/v4.5.1` commit with that
   key, then open the one literal PR. Do not push a tag.
4. Refactor A–H so each control and retained receipt has separate
   `trusted_workflow_sha` and `target_source_sha` fields. All phases must
   re-fetch the literal branches and exact PR/check/review state before any
   Environment or secret access.
5. Replace H's lightweight-tag creation contract with a reviewed procedure for
   one annotated, maintainer-signed tag that remains compatible with the tag
   ruleset. Review the Environment branch restrictions and keep publication
   authority unavailable until source admission is complete.
6. Run the complete negative workflow suite, Ruff, diff-check, and a dry run
   with all publication flags false. Only then may the contract change to
   `ACTIVE_FOR_ONE_V4_5_1_OPERATION` and its blocker list become empty.
7. After the immutable release and signed ledger are retained, return the lane
   to inert state. It is not a generic selector for later repositories,
   branches, versions, or tags.

Until these conditions are simultaneously true, the correct result is a
fail-closed blocker. The disabled legacy workflow is not an alternative.
