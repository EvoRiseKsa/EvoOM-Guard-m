# v4.5.1 maintenance-lane trust boundary

## Current decision

`v4.5.1` is **not publishable by the current A-H chain**. This change records
an inert Phase-0 model for a possible one-time maintenance operation. It is not
a live collector, an activated lane, or evidence that the modeled state exists.
It creates no branch, pull request, tag, release, repository variable, signing
authority, or GitHub setting.

The machine-readable model is
[`security/v4.5.1-maintenance-lane.json`](../security/v4.5.1-maintenance-lane.json).
Its local validator is
[`tools/ci/validate_v451_maintenance_control.py`](../tools/ci/validate_v451_maintenance_control.py).

## Why the existing chain cannot be reused unchanged

1. The current A-H workflows couple `GITHUB_WORKFLOW_SHA`, `GITHUB_SHA`, the
   protected `main` head, and the release target. A maintenance operation must
   instead execute reviewed workflow bytes from protected `main` while
   admitting a distinct source commit descended from the retained `v4.5.0`
   state.
2. Current H creates `refs/tags/v*` at a commit. That is a lightweight tag; it
   cannot prove a locally signed annotated tag object under a pinned maintainer
   key.
3. The maintenance branch and candidate PR do not exist. Their future live
   state therefore cannot be claimed by a repository snapshot.
4. GitHub's REST signature fields do not expose the maintainer key fingerprint
   required by this model. Signature verification must be performed locally on
   raw Git commit and tag objects with a pinned public key.

## What Phase 0 freezes

The model contains reviewed literal requirements rather than candidate-provided
claims:

- repository and owner IDs, trusted `main` ref, retained maintenance base
  commit and tree, candidate branch, version, and tag;
- the complete `main` branch-protection shape and exactly eleven required
  check/App-ID pairs;
- the `v*` tag ruleset, DeployKey-only bypass, and prohibited current-user
  bypass;
- all four protected Environments, reviewer IDs, and `main` deployment-branch
  policy. The workflows execute from trusted `main`; the Environments must not
  be switched to the untrusted maintenance branch;
- raw-Git modes and blob IDs for seven workflows and every frozen control,
  policy, and verifier-pack input;
- seven workflow runs in the order `A -> B -> CD -> E -> F -> G -> H`. C and D
  are jobs in the same CD workflow run;
- separate `trusted_workflow_sha` and `target_source_sha` identities in every
  run and handoff;
- an immutable release containing exactly `evo-guard.pyz`,
  `evo-guard.spdx.json`, and `SHA256SUMS` with digests bound to retained F/G
  admission bytes;
- a bounded, owner-authorized raw annotated tag object. H must verify that
  object locally, then push the tag **object SHA**, not the target commit SHA.

The model is deliberately pre-activation. Its trusted workflow commit/tree,
local signing-key path/blob/fingerprint, and one-shot enable value remain
`POST_MERGE_REQUIRED`. Those values may be pinned only after the reviewed bytes
land on protected `main`, by an explicit owner-authorized operation. A file in
the candidate branch cannot authorize itself.

## Three independent observation authorities

The validator does not accept one self-reported JSON snapshot as closed-world
proof. A future activation path must collect and validate three distinct inputs:

1. **Owner-authenticated control plane:** exact repository, refs, pull request,
   review, branch protection, check/App identities, ruleset, Environments, and
   run IDs/attempts.
2. **Raw Git:** commit/tree topology, path modes, old/new workflow and control
   blobs, patch bytes/digests, and the final tag object/ref binding.
3. **Local signature verification:** raw source-commit and annotated-tag
   verification against one pinned public key fingerprint.

Candidate output is not allowed to supply trusted workflow blob IDs, signer
login, signing fingerprint, protection state, or Environment state. A REST
`author.login`, `verification.verified`, or `verification.reason` value is not a
signer fingerprint and is not accepted as one.

## Activation blockers

The exact blockers are retained in the JSON model. At minimum, the reviewed
Phase-0 bytes must land on protected `main`; the post-merge commit/tree and
signing root must be owner-pinned; a bounded owner-authenticated collector must
exist; maintenance branch and candidate state must be created and independently
observed; and A-H must be redesigned so workflow identity and target identity
remain distinct through every handoff. H must consume a locally signed raw tag
object instead of constructing a lightweight tag.

Only a separate reviewed implementation may activate the lane. V2/V3 schemas,
the A-H redesign, branch creation, settings changes, signing-key operations, tag
creation, and release publication are intentionally outside Phase 0.

## Regression boundary

Tests reject alternate repositories, moved refs, duplicate PRs, stale reviews,
wrong App IDs, weakened protection/rulesets/Environments, raw-Git mode or blob
substitution, merge parents, out-of-scope paths, unsigned or wrong-key source
commits, stale attempts, a separate D run, lightweight/wrong-target/oversized or
wrong-key tags, asset-set expansion, digest mutation, and mutable releases.

Until every blocker is closed by independently obtained evidence, the only
correct result is fail-closed.
