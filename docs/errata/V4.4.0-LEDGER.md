## Local signing-key disposition

The unsigned
[`LEDGER_KEY_DISPOSITION.json`](../../evidence/release-operations/v4.4.0/LEDGER_KEY_DISPOSITION.json)
tracks only the operator-local file disposition of the unused prospective
`v4.4.0` ledger private key. It begins as `pending-operator-removal` and may be
updated to `local-file-removed` only after an operator observes removal of the
named external file. It is not `KEY_RETIREMENT.json`, a signed retirement
receipt, revocation evidence, deletion proof, secure-erasure proof, or evidence
that no copy exists. No standard retirement receipt can be issued because no
canonical `v4.4.0` ledger exists.

## Missing repository evidence

The protected source tree does **not** contain
`evidence/release-ledgers/v4.4.0/RELEASE_LEDGER.json`. Therefore it cannot
claim a signed v2 ledger for this publication, ledger-bound completion of the
protected A-through-H operation, or ledger-bound publication by that pipeline.
The newest validated repository ledger remains
`tests/baseline/v4.3.0/RELEASE_LEDGER.json`.

This absence does not undo the live immutable GitHub Release. It does prevent
the repository from treating that live state as if the missing signed ledger
already existed.

## Why no canonical v4.4.0 ledger can be issued

The release operation was bound to trusted parent commit
`163ad0591ac64cada35f0643683f3afff397e2d6`, tree
`df5821ec364e9d62a77bf3ee609a575583ae351a`, and validator blob
`d80180d7ce744fbc2f06dae44dce0718b2693fbf` at
`tools/ci/validate_release_ledger_v2.py`.

That frozen validator incorrectly required both GitHub Release `created_at`
and `published_at` to fall inside phase H. H run
[`30415174549/attempts/1`](https://github.com/EvoRiseKsa/EvoOM-Guard-m/actions/runs/30415174549/attempts/1)
observed the phase from `2026-07-29T01:49:58Z` through
`2026-07-29T01:55:52Z`. The actual `published_at`,
`2026-07-29T01:55:50Z`, falls inside that interval. The exact GitHub
`created_at`, `2026-07-29T01:30:39Z`, precedes it because that field is
target-commit metadata rather than a release-lifecycle event.

PR
[`#255`](https://github.com/EvoRiseKsa/EvoOM-Guard-m/pull/255) corrected that
semantic rule for future operations. It cannot be substituted retroactively:
the v4.4.0 descriptor and operation are cryptographically bound to the frozen
parent tree and old validator blob. Consequently:

- `canonical_ledger_issued = false`;
- `signature_issued = false`; and
- the terminal reason is
  `FROZEN_VALIDATOR_CREATED_AT_SEMANTICS_MISMATCH`.

## Safe recovery

1. Do not move `v4.4.0` or rewrite its release, assets, checksums, or
   attestations.
2. Keep generated consumer install and Action pins on the latest validated
   repository ledger (`v4.3.0`) until a later recovery release is ledgered.
3. Do not assemble, sign, or claim a canonical `v4.4.0` ledger with the
   corrected validator; that would rewrite the frozen release-operation
   contract after the fact.
4. Prepare `v4.4.1` from the corrected protected source, run a fresh protected
   A-through-H operation with the corrected trusted parent and validator, and
   issue a signed `v4.4.1` ledger only if that new operation validates.
5. After the `v4.4.1` ledger is committed and selected by
   `PROJECT_STATUS.json`, move the source to its new ledger-recorded release
   line and regenerate the documentation. Keep `v4.4.0` permanently recorded
   as `published-unledgered`.
