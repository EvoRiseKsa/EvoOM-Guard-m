# v4.4.1 release-ledger erratum

This is a post-publication correction record. It is **not** a release ledger.

## What remains valid

The immutable `v4.4.1` GitHub Release remains published at commit
`927aaf007c13d5dda10146456579030b14169a73`. Its three release assets,
checksums, GitHub release attestation, build provenance, tag CI, and action
smoke observations were independently rechecked. The bounded machine-readable
record is
`evidence/release-operations/v4.4.1/UNSEALED_STATUS.json`.

The protected A-through-H workflow runs completed successfully and 57 retained
evidence files were collected. Those facts do not create a valid release
ledger and are not a substitute for one.

## Why no v4.4.1 ledger exists

The exact validator frozen by the trusted parent cannot validate the retained
inputs from a clean interpreter:

1. It rejects the original CPython `pyexpat.errors` and `pyexpat.model`
   originless aliases during cold start.
2. It requires compact JSON bytes for six result files even though the frozen
   trusted release CLI emits strict deterministic indented JSON.

Changing the frozen validator or rewriting those retained files would change
the evidence contract after publication. Therefore no canonical `v4.4.1`
ledger or signature can be issued retroactively.

PR #259 corrected both defects prospectively at commit
`3a10df138e949e97af91597e5af1533abd90a3dd`. It does not validate or repair
`v4.4.1`.

## Signing-key boundary

The prospective `v4.4.1` ledger private-key file is unused and has no remaining
authorized signing purpose. Its current disposition is recorded as
`pending-operator-removal` in
`evidence/release-operations/v4.4.1/LEDGER_KEY_DISPOSITION.json`; no deletion,
secure erasure, revocation, or absence-of-copies claim is made.

At the first local custody review, an inherited local group ACL meant exclusive
offline custody at publication had not been established. The ACL was
subsequently restricted, which does not change the publication-time fact. This
is not a claim that the key was compromised.

## Recovery

Do not move `v4.4.1`, rewrite its release, alter its assets, or create a
retroactive ledger. Prepare `v4.4.2` with a new trusted parent, fresh benchmark
chain, distinct release-admission keys, and a distinct ledger signing key. Keep
`v4.4.1` permanently recorded as published-unledgered.
