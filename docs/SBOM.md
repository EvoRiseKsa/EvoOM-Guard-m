## What the generated document records

`ops/generate_spdx_sbom.py` is stdlib-only and reads the exact already-built
zipapp bytes. It emits:

- one SPDX package for `evo-guard.pyz`;
- one SPDX file for every regular ZIP member, in deterministic name order;
- SHA-1 and SHA-256 for every member and for the package artifact;
- the SPDX package verification code computed from all member SHA-1 values;
- the exact UTF-8 `LICENSE` text embedded in the zipapp as an extracted
  `LicenseRef`;
- one document `DESCRIBES` relationship and one package `CONTAINS`
  relationship for every member; and
- a unique namespace derived from the release version, zipapp SHA-256, and
  normalized UTC creation time derived from the release commit time.

The generated bytes are deterministic for the same zipapp bytes, canonical
version, and commit timestamp. The generator rejects links, special-file
entries, unsafe or ambiguous names, duplicate portable names, unsupported ZIP
flags/compression, metadata mismatches, overlapping local records, oversized
input, invalid UTF-8 license text, and non-finite JSON. It writes through a
same-directory temporary regular file and atomically replaces the destination
only after serialization and `fsync`.

The release byte contract uses EvoOM Guard's local canonical JSON encoding:
UTF-8, keys sorted lexicographically, no insignificant whitespace, non-ASCII
characters left unescaped, non-finite numbers forbidden, and one trailing LF.
This is not a claim of RFC 8785 conformance. The exact encoding lets admission
bind the SPDX predicate object returned by GitHub to the retained
`evo-guard.spdx.json` bytes without normalizing or rewriting evidence.

Tests validate the output against an unmodified official SPDX 2.3 JSON Schema
pinned to upstream commit
`aadf3b0b8dbbabdb4d880b0fc714255fea436ff7`, blob
`ee61e6686e885f8139c132647fd0b4f483b8fb81`. The vendored schema, exact upstream
license, and provenance notice live under `tests/schema/`; they are test
material and are not packaged into the zipapp.

## Verification for an SBOM-enabled release

<!-- BEGIN EVOGUARD_PROJECT_STATUS:SBOM_PIPELINE -->
Releases ship through the manually dispatched protected-release workflow
(`.github/workflows/release.yml`): tag-equals-version validation, the full test suite,
Linux and Windows end-to-end checks, a reproducible artifact build with checksums, and
asset attestation. It prepares a byte-verified draft, then a distinct protected
Environment approval authorizes a no-checkout job to revalidate live source,
tag-ruleset, signed-tag, and asset authority, publish, and prove exact immutable
readback. No release step is gated on dates, elapsed time, or stabilization windows. The
detached-maintainer-signed direct record for `v4.7.1` records successful workflow run
`33532737067` and post-publication byte readback. Its signature authenticates the exact
maintained record bytes, but the evidence remains a same-owner observation, not
independent validation or a protected A-through-H ledger. The archived A-H signed lane
is implemented in source but inert with every activation flag false; it is a design
reference, not the current release path. The deterministic SPDX generator exists in
source. The `v4.7.1` direct record reports the SPDX asset in the immutable release and
exact byte readback, while the provider SBOM attestation subject is only the zipapp. The
direct record does not claim provenance for the SPDX asset itself.

- build provenance whose subject is `evo-guard.pyz`; and
- an SBOM attestation whose subject is the same zipapp and whose predicate is
  `evo-guard.spdx.json`; and
- build provenance whose subject is `evo-guard.spdx.json` itself, so artifact
  admission can freshly verify those exact inventory bytes as an independent
  release asset.

Verify all three provider attestations against the exact repository, release
workflow, source ref, source commit, and GitHub-hosted-runner boundary. See
[GitHub Artifact Attestations](GITHUB_ARTIFACT_ATTESTATIONS.md).

## Non-claims

This SBOM is an **artifact-member inventory**, not:

- a source-tree, operating-system, Python interpreter, runner-image, or
  deployment inventory;
- dependency resolution, source composition analysis, license legal review,
  vulnerability scanning, exploitability analysis, or a VEX document;
- proof that an omitted or dynamically loaded component cannot affect runtime;
- proof of correctness, security, non-maliciousness, admission, publication
  authority, or deployment authority; or
- evidence of independent construction or review. The zipapp and SBOM share
  the same unprivileged build provenance; moving attestation to a separate
clean runner isolates provider authority but does not make the evidence
independent.

Cross-job transfers are pinned to the immutable GitHub artifact ID emitted by
the upload step, with digest mismatch configured as fatal. The publication job
can download only the artifact ID approved after the clean verification step.

The deterministic generator does not establish cross-platform reproducible
builds. Checkout line endings, Python, ZIP implementation, OS, and toolchain
differences can change zipapp bytes and therefore the namespace, hashes, and
SBOM bytes.
The tag-triggered CI check proves a narrower fact: the published immutable
assets byte-match a rebuild performed by the configured GitHub workflow.
