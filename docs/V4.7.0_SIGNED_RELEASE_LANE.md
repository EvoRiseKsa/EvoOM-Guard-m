# v4.7.0 signed minor-release lane

## Status

This is an inert, fail-closed parent contract. It is not evidence that the
fourteen-day stabilization window has started, that GitHub recognizes the
maintainer key, that a signed candidate or tag exists, or that `v4.7.0` has
been published.

The lane also remains inert until `main` has been migrated from classic branch
protection to the exact ruleset-only contract described below. A generic
`DeployKey` ruleset bypass does not bypass a simultaneously active classic
branch-protection rule, so leaving both enabled would make the signed-source
push fail rather than provide defense in depth.

The private maintainer signing key is deliberately absent from the repository,
GitHub Actions, repository secrets, and protected Environments. Its current
custody model is one ACL-protected local operational copy plus a removable
backup. This is not a hardware-only, non-exportable, or single-copy key claim.

The public SSH signing root is frozen by
[`v4.7.0.json`](../security/release-maintainer-roots/v4.7.0.json) and
[`v4.7.0.pub`](../security/release-maintainer-roots/v4.7.0.pub). The repository
uses LF bytes; their SHA-256 is
`f5a137810263756bcfbee4ebb020ca3c26a40d6876a5972ff2baa4d0ef7b0cab`.
The supplied CRLF source copy has a different byte digest recorded only as a
custody observation. The cryptographic OpenSSH fingerprint is
`SHA256:iCn7wa6HgKdu7luf/16rrKZzSk5FygJoA8EKNl3LJ24`.

Before activation, that public key must be added to the `EvoRiseKsa` GitHub
account as a **signing key**, not merely an authentication key. Every release
gate requires both local verification against the pinned repository root and
GitHub `verified=true`, `reason=valid`. Registration is currently an external
pending prerequisite; unavailable verification blocks the release.

## Why promotion precedes A

The product release commit must retain its maintainer signature and have one
parent. GitHub squash and rebase merges create different commits, while a merge
commit has two parents. The protected
`evoguard-promote-signed-release-source.yml` workflow therefore accepts an
already reviewed, already signed immutable commit and fast-forwards `main` to
that exact SHA. It never possesses the maintainer signing key.

Before its temporary source-promotion deploy key becomes visible, the workflow
requires all of the following:

- current protected `main` equals the owner-pinned freeze declaration commit
  and tree;
- the candidate is exactly one child of that commit;
- the v4.7.0 freeze validator proves the complete fourteen-day window elapsed;
- the candidate changes only the exact stable-promotion scope and performs only
  the literal `4.7.0.dev0` to `4.7.0` version assignment in executable source;
- GitHub reports a valid signature associated with the frozen maintainer
  account, while the parent-owned local verifier independently verifies the raw
  commit object against the pinned public key;
- one open, non-draft, same-repository PR has that exact head and unchanged
  base, `MANA-awam` approved that exact head, all review threads are resolved,
  GitHub's aggregate `reviewDecision` is `APPROVED`, its `mergeStateStatus` is
  `CLEAN`, and the eleven frozen check/App-ID pairs are uniquely successful;
- the protected Environment approval completes without any relevant ref,
  review, check, signature, or authorization change.

The final job derives the public key and OpenSSH fingerprint from
`EVOGUARD_RELEASE_SOURCE_DEPLOY_KEY`, compares it to the exact owner variable,
rechecks fast-forward ancestry and live `main`, and pushes only
`candidate_sha:refs/heads/main`. A then independently verifies the same raw
signature and freeze again before candidate execution.

### Executable `main` protection contract

Before P is enabled, create exactly one active repository branch ruleset named
`EvoOM Guard main signed-source authority`, targeting only `refs/heads/main`.
Its only bypass actor is the generic `DeployKey` actor (`actor_id=null`,
`bypass_mode=always`); there is no administrator, role, user, team, or App
bypass. Its exact rules are creation/deletion restrictions, non-fast-forward
blocking, linear history, the existing pull-request review requirements, and
the eleven strict status-check/App-ID pairs. It does **not** impose a global
signed-commit rule: exact release-object signatures remain independently
enforced by P and A, while ordinary project commits keep the existing policy.

After the ruleset is active and its ordinary PR behavior has been verified,
remove classic protection from `main`; the classic protection endpoint must
then return exactly HTTP 404. Configure a short-lived fine-grained
`EVOGUARD_RELEASE_SOURCE_CONTROL_PLANE_TOKEN` for this repository with
`Administration:read` only in the promotion Environment. P makes only bounded
GET requests with it. Immediately before the push, P proves all of the
following from the authenticated live API and a parent-owned validator:

- classic branch protection is absent;
- the complete repository/inherited branch-and-push ruleset inventory contains
  exactly the one active ruleset above;
- the effective rules on `main` are exactly those rules and come from that ID;
- the generic bypass is exactly `DeployKey/always`;
- the repository has exactly one enabled write deploy key, with the pinned ID,
  verified Ed25519 public bytes, and fingerprint;
- the live `main` SHA is still the frozen declaration commit.

Preflight freezes the public source-key ID/fingerprint and main-ruleset ID once
as job outputs. A no-secret step repeats the control validation immediately
before key exposure and uploads a closed active-authority snapshot/receipt. The
private transport key is then derived only in the short push step and must match
that frozen public fingerprint. P uses a lease bound to the observed base,
parses the one reported ref mutation, re-reads `main` after it, and captures a
second live snapshot. P cannot finish successfully at that point. Its separate protected
retirement job remains pending until an operator deletes the source deploy key
and removes the generic `DeployKey` bypass from the main ruleset; parent-owned
code then captures a fresh complete inventory, proves zero enabled write keys
and the exact retired key ID absent, downloads the exact active artifact, and
retains a five-file terminal artifact whose binding proves that the active and
retired snapshots use the same ruleset/key identity and exact P run.
Once the closed active-authority artifact exists, the retirement job uses
`always()` semantics and runs on ordinary failure even if the promotion job
does not complete. It accepts only `main` still at the frozen base or already
at the exact candidate and records the observed terminal SHA. The base state
records `promotion_completed=false`, proves retirement, and still makes P fail
overall; only the candidate state records `promotion_completed=true` and is
admissible to downstream release publication. Before the closed active artifact
exists, P makes no terminal-closure guarantee.
A final no-secret closure job rejects the workflow unless the post-push
capture, validation, and closed evidence upload all succeeded and the
retirement job completed. The post-push steps remain best-effort only so their
failure cannot prevent the higher-priority authority retirement from running;
their outcomes are nevertheless mandatory for terminal workflow success.
A downloads and validates that exact terminal artifact by P run ID/attempt,
derives the frozen identity from its binding, and independently repeats the
live retirement proof before executing candidate bytes. These observations
narrow but cannot make the GitHub control plane transactional. A force-cancel,
runner loss, or API outage can still prevent `always()` retirement; such a run
is not admissible and requires explicit operator retirement/reconciliation
before another attempt.

## Verifiable freeze declaration

The parent-contract merge leaves
[`security/release-freezes/v4.7.0.json`](../security/release-freezes/v4.7.0.json)
in the inert `POST_MERGE_DECLARATION_REQUIRED` state. A separate protected
release-record-only PR must replace all four placeholders and set `state` to
`FROZEN`.

That declaration commit must:

1. have exactly one parent: the final parent-contract commit;
2. change only `security/release-freezes/v4.7.0.json` with mode `100644`;
3. record that parent commit and tree exactly;
4. retain the exact eleven-path stable-promotion scope;
5. declare that only release-record corrections are permitted during the
   stabilization window;
6. choose a canonical whole-second UTC `started_at` no earlier than, and no
   more than one hour after, its eventual commit time;
7. set `not_before` to exactly `started_at + 1,209,600 seconds`.

Choose `started_at` slightly in the future and merge the declaration before
that instant. If the merge misses the declared instant, create a new
declaration commit and restart the clock. After merge, pin its exact SHA/tree in
`EVOGUARD_V470_FREEZE_DECLARATION_SHA` and
`EVOGUARD_V470_FREEZE_DECLARATION_TREE_SHA`. The clock is established by the
committed record, raw Git history, and GitHub's server-time evidence, not by a
comment or manual assertion.

`release-record-corrections-only` is a repository change restriction, not
permission to preserve elapsed time across a correction. Any correction must
become a new exact declaration commit, receive a new exact GitHub push anchor,
be re-pinned, and restart the full fourteen-day clock.

Git commit `%ct` is owner-controlled and is therefore only a sanity check. P
and A both perform a complete, bounded Actions search for `event=push`,
`branch=main`, and the exact declaration `head_sha`. Every returned exact-head
run must be unique, attempt 1, terminal `success`, and bound to this repository.
The inventory is exactly the post-merge numeric workflow IDs for `Windows
compatibility` (`.github/workflows/windows.yml`), `CodeQL`
(`.github/workflows/codeql.yml`), `CI` (`.github/workflows/ci.yml`), and
`ClusterFuzzLite PR fuzzing` (`.github/workflows/cflite_pr.yml`). GitHub's live
run `path` values are repository-relative paths without an `@main` suffix.
The latest GitHub `created_at` must be no later than `started_at`, while
`started_at` must be no more than one hour after the earliest `created_at`.
The validator also rechecks the fourteen-day boundary and refuses a stale
snapshot. Thus backdating the Git commit and the record cannot start or satisfy
the stabilization window.

The schema is
[`minor-release-freeze-v1.schema.json`](../tests/baseline/schema/minor-release-freeze-v1.schema.json),
and the authoritative cross-field/raw-Git check is
[`validate_minor_release_freeze.py`](../tools/ci/validate_minor_release_freeze.py).
The independent server-time check is
[`validate_release_freeze_github_anchor.py`](../tools/ci/validate_release_freeze_github_anchor.py),
fed only by the bounded capture in
[`capture_minor_release_freeze_anchor.js`](../tools/ci/capture_minor_release_freeze_anchor.js).

## Local release-commit signing

Work from the exact active freeze declaration commit and keep the signing key
outside the worktree. Configure SSH signing only for the release command, for
example in PowerShell:

```powershell
$key = "$HOME\.ssh\evorise-maintainer-signing-v1"
git switch --detach $env:EVOGUARD_V470_FREEZE_DECLARATION_SHA
git switch -c release/v4.7.0
# Apply only the exact stable-promotion files and render status documents.
git -c gpg.format=ssh -c user.signingkey=$key commit -S -m "release: v4.7.0"
git verify-commit HEAD
```

Do not use a merge, squash, amend, or rebase after approval. Push that exact
commit to a same-repository branch, open the PR, wait for the required checks,
obtain exact-head approval, set
`EVOGUARD_RELEASE_SOURCE_PROMOTION_ENABLED` to its 40-hex SHA, and dispatch the
promotion workflow from protected `main` with the SHA and PR number.

The temporary source deploy key is a transport/promotion key, not the
maintainer signing key. H's tag transport key is a third distinct key: the
maintainer signing, source-promotion transport, and tag-publication transport
fingerprints must be pairwise different, and neither transport private key may
be used to sign the release objects. After the exact main update and P's post-push snapshot,
delete that deploy key first, then remove the generic DeployKey bypass from the
`main` ruleset, approve only the retirement Environment, and require P's
terminal closure receipt. Remove the source private-key secret and one-shot
authorization, but retain the read-only observer plus the frozen source-key and
ruleset IDs through A and H. Do this before installing H's separate tag deploy
key; otherwise a tag-only key would also inherit the generic branch bypass. A
fresh authority and a fresh live proof are required for any future promotion
window.

## Local annotated-tag signing and raw-object handoff

After the admitted source SHA is final, create the annotated tag locally but do
not push its ref:

```powershell
$key = "$HOME\.ssh\evorise-maintainer-signing-v1"
$target = git rev-parse refs/heads/main
git -c gpg.format=ssh -c user.signingkey=$key tag -s `
  -m "EvoOM Guard v4.7.0" v4.7.0 $target
git verify-tag v4.7.0
git rev-parse 'v4.7.0^{tag}'
```

Export the exact raw tag-object payload with Git Bash or another byte-preserving
redirect; do not use a text-mode redirect that can rewrite line endings:

```sh
tag_object_sha="$(git rev-parse 'v4.7.0^{tag}')"
git cat-file tag "$tag_object_sha" > signed-tag-object
test "$(git hash-object -t tag signed-tag-object)" = "$tag_object_sha"
```

Base64-encode those exact bytes and set only these owner-controlled variables:

- `EVOGUARD_V470_SIGNED_TAG_OBJECT_B64`: canonical Base64 of the raw object;
- `EVOGUARD_V470_SIGNED_TAG_OBJECT_SHA`: the exact tag-object SHA.

The decoded object must not exceed 32,768 bytes. H decodes it canonically,
recomputes its Git object ID, parses and binds `object`, `type`, `tag`, `tagger`,
`message`, `encoding`, and signature, and verifies it locally twice against the
parent-pinned key before the publication secret is exposed. H then writes the
already signed object into a bare repository and pushes
`tag_object_sha:refs/tags/v4.7.0`. It does not sign in Actions and never pushes
the target commit as a lightweight tag.

Immediately before the publication step may reference the tag transport
secret, H uses the retained Administration-read observer to capture the whole
bounded branch/push ruleset, tag ruleset, and deploy-key inventories. A
parent-owned fail-closed verifier requires: the exact main ruleset with no
bypass, the retired source-key ID absent, exactly one active tag ruleset named
`EvoOM Guard release tag authority` covering only `refs/tags/v*`, its sole
generic bypass equal to `DeployKey/always`, and exactly one enabled verified
write deploy key with the pinned H ID and Ed25519 fingerprint. H does not trust
mutable repository variables for the retired source identity: it extracts the
exact P run from the admitted `source.json`, downloads that run's terminal
retirement artifact, validates its closed hashes and receipt, and carries the
derived source ID and fingerprint in the publication-ready record. H captures and
validates the same authority again after immutable publication, and uploads
both snapshots and canonical verification receipts. The observer is read-only
and never receives either transport private key. H also rejects a tag
transport fingerprint equal to either the frozen maintainer signing root or
the retired source-promotion transport fingerprint, including a source key
reinstalled under a different GitHub key ID.

If a later step fails after exact draft creation but before the PATCH boundary,
H removes only that exact still-draft release after rechecking its ID, body,
author, target, complete assets, and exact tag absence. If the PATCH marker
exists or any state is ambiguous, H preserves the release and requires manual
recovery; it never uses the tag private key merely to clean a pre-secret draft.

Before immutable publication H requires the Git ref to point to an object of
type `tag` with that exact object SHA, the object to peel to the admitted commit,
and GitHub to report `verified=true`, `reason=valid` with non-empty signature
and payload. Pre-publication cleanup uses a lease on the tag-object SHA. After
the release PATCH begins, H performs no automatic destructive recovery.

## Required external configuration and retirement

All bootstrap flags remain false until their exact operation. The parent tree
lists every post-merge workflow ID/blob, freeze SHA/tree, runtime/tool pin,
Environment, public root, raw-tag variable, and deploy-key fingerprint that
must be resolved from protected Git or the authenticated GitHub control plane.

The generic `DeployKey` ruleset bypass is acceptable on `main` only during P
while a complete, bounded, fully paginated owner-authenticated listing proves
the intended key is the sole write-enabled repository deploy key. The
promotion Environment has exactly the transport-key secret and the
administration-read observer secret. The workflow's derived-key fingerprint
check does not replace the live control-plane proof. During H the generic
`DeployKey` bypass belongs only to the exact `v*` tag ruleset; the main ruleset
must expose no bypass at all.

After H and durable ledger validation, disable the one-shot authorization,
delete the raw-tag Base64/SHA variables, remove the publication deploy key and
observer, Environment secrets, and frozen authority variables, and retain a
separately signed retirement observation. None of the source in this contract
proves that live configuration or retirement has occurred.
